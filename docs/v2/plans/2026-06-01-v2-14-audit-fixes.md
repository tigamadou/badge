### Task 1 — Securiser secrets plateforme

**But** : empecher tout `STAFF_ADMIN` non `SUPER_ADMIN` de modifier `smtpPassword` ou `recaptchaSecretKey`. Ajouter une re-authentification pour afficher les secrets.

**Steps** :
1. Dans `src/app/api/staff/settings/route.ts`, split le schema Zod du PATCH en deux : `patchSchemaCommon` (champs publics) et `patchSchemaSecrets` (smtpPassword, recaptchaSecretKey).
2. Logique :
   - Si le body contient un champ de `patchSchemaSecrets`, exiger `ctx.staffRole === "SUPER_ADMIN"` (sinon 403).
   - Sinon, conserver `withStaffAuth({ minRole: "STAFF_ADMIN" })`.
3. Test d'integration : STAFF_ADMIN PATCH smtpPassword -> 403 ; SUPER_ADMIN PATCH smtpPassword -> 200.
4. Dans `src/components/staff/PlatformSettingsForm.tsx`, le toggle "Afficher smtpPassword" doit ouvrir une modale demandant le mot de passe de l'utilisateur courant. Apres verification cote serveur (nouvelle route `POST /api/auth/verify-password`), les secrets sont decoded.
5. Tests Vitest sur la modale (toggle ferme par defaut, ouvre modale, soumet le mot de passe).

**Critere d'acceptation** :
- HTTP 403 pour STAFF_ADMIN qui tente de PATCHer un secret.
- HTTP 200 pour SUPER_ADMIN.
- Toggle "Afficher" requiert re-auth.

- **Ordre d'execution** : strictement par sévérité. Une regression en Critique (sécurité) doit bloquer la livraison ; une regression en Faible peut etre patchee post-cut-over.
- **Tests** : pour chaque task, le critere d'acceptation inclut des tests d'integration. Ne pas marquer `[x]` sans tests verts.
- **Commits** : un commit par task validee. Permet rollback granulaire si une regression apparait.
- **Dependances** : Task 3 et Task 7 dependent des ADR (Task 0 doit etre validee avant). Task 14 dependant de Task 2 (matrice MANAGER) sur les pages activity / members.
- **Estimation** : ~5-7 jours de travail focalise (Critique 1-2j, Eleve 2-3j, Moyen 1-2j, Faible 0.5j).
