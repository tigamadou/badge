> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Mettre en place une politique de tests obligatoire (3 couches : unitaires Vitest, integration API Vitest + vraie MySQL, E2E Playwright) et une CI GitHub Actions a 4 jobs paralleles bloquants (`lint`, `typecheck`, `unit`, `e2e`), tout en supprimant les vestiges Cypress jamais initialises.

**Architecture:** Le runtime de tests garde Vitest pour unit + integration ; Playwright est ajoute pour l'E2E avec une seule cible navigateur (chromium). La CI tourne sur GitHub Actions (`ubuntu-latest`), avec un service MySQL 8 pour les jobs `unit` et `e2e`, un cache yarn partage, et `concurrency.cancel-in-progress` par branche. La politique de tests est inscrite dans `CLAUDE.md` projet (specificites Badge) et le template `.claude/CLAUDE.md` (regle transverse). Les branch protection rules cote GitHub sont documentees dans un nouveau fichier `docs/v2/ci.md` mais configurees manuellement (le repo ne peut pas s'imposer une protection seul).

**Tech Stack:** Vitest 4 (deja en place), `@playwright/test` ^1.49.0 (a installer), MySQL 8 (service Docker en CI), GitHub Actions, Node.js 22, Yarn via Corepack, Make. Pas de seuil de couverture chiffre, pas de tests visuels, pas de multi-navigateur au demarrage.

**Spec:** [`docs/v3/specs/2026-05-31-v3-03-tests-et-ci.md`](../specs/2026-05-31-v3-03-tests-et-ci.md)

```typescript
import type { Page } from "@playwright/test";
import { expect } from "@playwright/test";
import type { TestUser } from "../fixtures/users";

// Connecte un utilisateur via le formulaire de login standard.
// Suppose que la page /login expose des champs name="email" et name="password" + bouton type="submit".
// A adapter si le selecteur change (cf src/app/(auth)/login/page.tsx ou equivalent).
export async function loginAs(page: Page, user: TestUser): Promise<void> {
  await page.goto("/login");
  await page.fill('input[name="email"]', user.email);
  await page.fill('input[name="password"]', user.password);
  await Promise.all([
    page.waitForURL((url) => !url.pathname.startsWith("/login"), { timeout: 10000 }),
    page.click('button[type="submit"]'),
  ]);
  // On verifie que NextAuth a bien pose un cookie de session.
  const cookies = await page.context().cookies();
  const sessionCookie = cookies.find(
    (c) =>
      c.name.includes("next-auth.session-token") ||
      c.name.includes("__Secure-next-auth.session-token")
  );
  expect(sessionCookie, "next-auth session cookie absent apres login").toBeDefined();
}
```

- [ ] **Step 4.4: Creer `e2e/support/db.ts`**

Contenu de `e2e/support/db.ts` :

```typescript
import { execSync } from "node:child_process";

// Reset complet de la BDD de test : drop + push + seed.
// Utilise par des hooks beforeAll() sur les suites qui ont besoin d'un etat propre.
// En CI le DB est deja seedee une fois avant le job ; cette fonction permet aux tests
// locaux iteratifs de retrouver un etat connu sans repasser par make.
//
// Attention : cette fonction est destructive. NE PAS l'appeler contre une BDD non-test.
// Garde-fou : on refuse de tourner si DATABASE_URL contient "prod" ou pointe sur 173.212.217.54.
export function resetDb(): void {
  const dbUrl = process.env.DATABASE_URL ?? "";
  if (!dbUrl) {
    throw new Error("resetDb() : DATABASE_URL non defini");
  }
  if (dbUrl.includes("prod") || dbUrl.includes("173.212.217.54")) {
    throw new Error(
      `resetDb() : refus, DATABASE_URL ressemble a une URL de prod (${dbUrl})`
    );
  }
  execSync("npx prisma db push --force-reset --skip-generate", { stdio: "inherit" });
  execSync("npx tsx prisma/seed.ts", { stdio: "inherit" });
}
```

### Trois couches obligatoires

| Couche | Outil | Périmètre obligatoire | Localisation |
|---|---|---|---|
| **Unitaires** | Vitest | Tout helper de `src/lib/`, toute fonction métier non triviale, toute logique pure (formatters, validateurs, parseurs, mappers) | `src/**/__tests__/*.test.ts` |
| **Intégration API** | Vitest + vraie BDD MySQL | Toute route `src/app/api/**/route.ts` créée ou modifiée — au minimum le golden path + au moins **un cas d'autorisation refusée** (401/403) | `src/app/api/**/__tests__/*.test.ts` ou `tests/integration/**/*.test.ts` |

### Règle générale

Une PR sans test couvrant le changement est **rejetée par la review**, sauf exception explicite déclarée dans la description :

- Changement purement documentaire (`docs/`, `README.md`, commentaires).
- Changement purement cosmétique (CSS sans logique, copie texte UI).
- Changement de configuration sans logique exécutable (`.gitignore`, `Caddyfile`, `docker-compose*.yml`, `Dockerfile*`).
- Reformattage automatique (Prettier, ESLint --fix sans changement de comportement).

L'exception **doit être déclarée explicitement** dans la PR. Pas d'exception implicite.

### Critères qualité

- **Pas de mock de l'ORM ou des règles métier critiques** : les tests d'intégration utilisent une vraie BDD MySQL.
- **Pas de test creux** : un test qui ne ferait que vérifier `mock.toHaveBeenCalled()` sans valider d'effet observable est rejeté.
- **Golden path d'abord** : on couvre le cas nominal avant les edge cases.
- **RBAC** : toute route protégée doit avoir au moins un test d'intégration qui vérifie qu'un user non autorisé reçoit 401/403.

## Risques connus et garde-fous

1. **Le test E2E de Task 5 echoue parce que le seed ne cree pas le user attendu** : c'est le risque le plus probable. Mitigation : Step 4.1 verifie le seed avant les fixtures, Step 5.1 verifie l'existence du user en BDD. Soit on adapte les fixtures, soit on adapte le seed (le seed change impact d'autres tests : prevenir l'utilisateur si modification).
2. **Les selecteurs de la page login (`input[name="email"]`, etc.) ne matchent pas l'UI actuelle** : Mitigation : Step 4.3 inspecte l'UI avant d'ecrire le helper, Step 5.4 documente comment iterer sur le helper.
3. **Le job `e2e` en CI met > 8 min** : Mitigation : duree cible dans `docs/v2/ci.md`, alerte au-dela. Si depasse souvent : sharding Playwright (`yarn test:e2e --shard=1/2` + matrix de jobs).
4. **Les noms de jobs requis pour la branch protection n'apparaissent qu'apres un premier run** : documente dans `docs/v2/ci.md` (Step "Verification post-activation").
5. **Le PAT GitHub n'est pas requis pour la CI** (au contraire de Kamal v3-02) : la CI tourne avec le `GITHUB_TOKEN` auto-injecte. Aucun secret a configurer dans `Settings -> Secrets`.
6. **`yarn install --frozen-lockfile` echoue en CI** si le `package.json` est modifie sans `yarn.lock` correspondant. Mitigation : toujours commiter `yarn.lock` avec `package.json` (deja fait Task 2 Step 2.5).
7. **`webServer` Playwright vs orchestration CI** : on a choisi de ne **pas** utiliser le bloc `webServer` du config Playwright et d'orchestrer `yarn build` + `yarn start` + `wait-on` directement dans le job CI. Raison : meilleur controle du process en CI (logs uploades en cas d'echec via `app.log`), et evite que Playwright relance l'app en local quand le dev a deja `make dev` actif. Si on revient en arriere : retirer les steps "Build app", "Start app (background)", "Wait for app", "Stop app" du job e2e et ajouter le bloc `webServer` dans `playwright.config.ts`.
8. **Conflit avec d'autres workflows futurs** : `concurrency.group: ci-${{ github.ref }}` est specifique au workflow CI. Si d'autres workflows sont ajoutes plus tard (cron backups, deploy Phase 2), ils auront leur propre group.
