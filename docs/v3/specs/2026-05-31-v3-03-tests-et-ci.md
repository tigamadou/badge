# Spec v3-03 — Politique de tests et CI GitHub Actions

> **Statut** : conception validée — 2026-05-31
> **Type** : règle transverse projet (politique qualité + workflow CI)
> **Périmètre** : v1 et v2 — la règle s'applique à tout code du repo, indépendamment de la version doc active
> **Spec maîtresse** : [`docs/v2/specs/2026-05-28-v2-master-design.md`](../../v2/specs/2026-05-28-v2-master-design.md) (non bloquante : cette spec ne modifie aucun modèle métier)
> **Specs liées** :
> - v3-02 (déploiement Kamal) — la CI ne déploie pas (Phase 1 = déploiement local), elle vérifie uniquement la qualité
> - Toutes les sous-specs v2 — la nouvelle politique s'applique à leur implémentation

## Contexte et objectifs

Le projet a aujourd'hui :

- **Vitest** configuré avec une poignée de tests unitaires (`src/lib/__tests__/`) couvrant 5 helpers : `auth`, `mail`, `qrcode`, `format-badge-name`, `generate-id`.
- **Cypress** présent dans `cypress/` mais **non installé** (deps absentes du `package.json`, sous-dossiers `e2e/` `support/` `fixtures/` vides).
- **Aucune CI hébergée** (pas de `.github/workflows/`).
- **Commandes locales** : `make lint`, `make typecheck`, `make test` qui tournent dans le conteneur dev.

Conséquence : rien n'empêche aujourd'hui de merger une PR qui casse le lint, le typecheck ou les tests. La qualité repose entièrement sur la discipline du dev qui pousse. Sur un projet SaaS multi-tenant qui démarre (v2), c'est un risque opérationnel direct — un bug RBAC mergé sans test peut fuiter de la donnée entre organisations.

Cette spec définit :

1. Une **politique de tests obligatoire** inscrite dans `CLAUDE.md` (spécificités projet) et dans le template générique `.claude/CLAUDE.md` (règle transverse).
2. La **migration Cypress → Playwright** pour les tests fonctionnels E2E (Cypress n'a jamais été initialisé, on part proprement sur Playwright qui est plus rapide en CI et mieux outillé pour Next.js).
3. La **mise en place d'une CI GitHub Actions** qui bloque les merges si un job échoue.
4. Les **commandes Makefile** associées et la documentation de configuration des **branch protection rules** côté GitHub.

## Décisions tranchées (synthèse ADR)

| Sujet | Décision | Pourquoi |
|---|---|---|
| Framework E2E | **Playwright** (remplace Cypress non-installé) | Plus rapide en CI (parallélisme natif), API plus moderne, meilleur support TypeScript et Next.js, gestion des traces/screenshots out-of-the-box, pas de runner externe. Cypress n'a jamais été initialisé donc pas de sunk cost. |
| Périmètre "tests fonctionnels" | **E2E navigateur + tests d'intégration API** | E2E pour les parcours UI critiques (login, inscription publique, scan badge), intégration API (Vitest + vraie BDD) pour les routes `src/app/api/**/route.ts`. Les deux couches sont complémentaires : l'intégration valide les contrats serveur, l'E2E valide le parcours réel. |
| BDD pour tests d'intégration et E2E | **MySQL 8 (vrai, pas de mock)** | Cohérence avec la prod. Mock = piège connu (cf. règle déjà inscrite : "pas de mock de l'ORM ou des regles metier critiques"). En CI on lance un service MySQL 8. |
| Plateforme CI | **GitHub Actions** | Repo déjà sur GitHub (cf. spec v3-02, registry GHCR). Gratuit pour repos privés dans la limite des minutes. Bonne intégration branch protection. |
| Architecture du workflow | **4 jobs parallèles** : `lint`, `typecheck`, `unit`, `e2e` | Feedback rapide sur tous les axes en un run. Échec d'un job n'empêche pas les autres de remonter leurs problèmes. Cache yarn partagé par job. |
| Concurrence des runs | `cancel-in-progress: true` par branche | Un nouveau push annule l'ancien run en cours. Évite de gaspiller des minutes CI sur du code obsolète. |
| Trigger | `pull_request` vers `development` et `main`, `push` sur `development` et `main` | Couvre les PR en cours + les pushs directs (rare, mais utile pour les hotfix sur main). |
| Niveau d'exigence | **Tests unit + un test fonctionnel golden path obligatoires** pour tout helper/route/feature nouveau ou modifié | Strict mais pragmatique. Pas de seuil de couverture chiffré (génère des tests creux). Exception : changements purement documentaires/cosmétiques/config explicitement marqués. |
| Branch protection | Documentée mais **configurée manuellement côté GitHub** | Le repo ne peut pas s'imposer une branch protection seul. La spec et la doc de CI précisent la liste exacte des status checks à exiger. |
| Suppression du dossier Cypress | **Oui, supprimé en clean** | Dossier vide, jamais initialisé. Aucun risque de perte. |

## Section 1 — Politique de tests (texte normatif)

Cette section est la **source de vérité** pour ce qui sera inséré dans `CLAUDE.md` projet et `.claude/CLAUDE.md` template. Toute évolution future de la politique passe par modification de cette spec d'abord.

### 1.1 Trois couches de tests

| Couche | Outil | Périmètre obligatoire | Localisation |
|---|---|---|---|
| **Unitaires** | Vitest | Tout helper de `src/lib/`, toute fonction métier non triviale, toute logique pure (formatters, validateurs, parseurs, mappers) | `src/**/__tests__/*.test.ts` |
| **Intégration API** | Vitest + vraie BDD MySQL | Toute route `src/app/api/**/route.ts` créée ou modifiée — au minimum le golden path + au moins **un cas d'autorisation refusée** (401/403) | `src/app/api/**/__tests__/*.test.ts` ou `tests/integration/**/*.test.ts` (à arbitrer en plan d'impl.) |
| **E2E** | Playwright | Toute feature UI nouvelle ou modifiée — au minimum **un parcours golden path** dans un vrai navigateur | `e2e/**/*.spec.ts` |

### 1.2 Règle générale

Une PR sans test couvrant le changement est **rejetée par la review**, sauf si elle entre dans l'une de ces exceptions explicitement déclarées dans la description :

- Changement purement documentaire (`docs/`, `README.md`, commentaires).
- Changement purement cosmétique (CSS sans logique, copie texte UI).
- Changement de configuration sans logique exécutable (`.gitignore`, `Caddyfile`, `docker-compose*.yml`, `Dockerfile*` — sauf si on introduit du code dans un entrypoint).
- Reformattage automatique (Prettier, ESLint --fix sans changement de comportement).

L'exception **doit être déclarée explicitement** dans la PR (case à cocher ou phrase dédiée). Pas d'exception implicite.

### 1.3 Critères qualité des tests

- **Pas de mock de l'ORM ou des règles métier critiques** (règle déjà existante, on la rappelle). Les tests d'intégration utilisent une vraie base de données de test.
- **Pas de test creux** : un test qui ne ferait que vérifier que `mock.toHaveBeenCalled()` sans valider d'effet observable est rejeté.
- **Golden path d'abord** : on couvre le cas nominal avant les edge cases. Edge cases couverts uniquement si le code les gère explicitement.
- **RBAC** : toute route protégée doit avoir au moins un test d'intégration qui vérifie qu'un user non autorisé reçoit 401/403.

### 1.4 Exécution locale (commandes obligatoires avant commit)

```
make lint        # ESLint
make typecheck   # tsc --noEmit
make test        # Vitest run (unit + integration)
make test-e2e    # Playwright (E2E)
```

Les quatre doivent passer. Un échec ailleurs qu'en local est traité comme un bug local à corriger, pas comme un problème CI.

## Section 2 — Migration Cypress → Playwright

### 2.1 Suppression de l'existant

- Supprimer le dossier `cypress/` (vide).
- Mentionner explicitement la suppression dans le commit.

### 2.2 Installation Playwright

DevDependencies à ajouter au `package.json` :

```
"@playwright/test": "^1.49.0"
```

Au premier `yarn install` + `npx playwright install chromium` télécharge les binaires navigateur.

### 2.3 Structure cible

```
playwright.config.ts
e2e/
├── fixtures/
│   └── users.ts              # données de seed pour les tests (emails, mots de passe)
├── support/
│   ├── auth.ts               # helper loginAs(page, user)
│   └── db.ts                 # helper resetDb() entre tests
├── login.spec.ts             # parcours golden path : login → redirection dashboard
├── public-registration.spec.ts  # /e/[slug] : inscription publique golden path
└── ...                       # un fichier par feature E2E
```

### 2.4 `playwright.config.ts`

Points clés :

- `testDir: './e2e'`
- `baseURL: process.env.E2E_BASE_URL ?? 'http://localhost:3000'`
- `webServer` : en CI uniquement, lance `yarn build && yarn start` avant les tests. En local, suppose l'app déjà lancée via `make dev`.
- `projects` : `chromium` uniquement au début. Firefox/Webkit ajoutés ultérieurement si besoin réel.
- `use.trace: 'on-first-retry'` — traces conservées pour les échecs.
- `reporter: [['list'], ['html', { outputFolder: 'playwright-report' }]]` — rapport HTML uploadé en artefact CI sur échec.

### 2.5 Scripts npm

Ajouts au `package.json` :

```
"test:e2e": "playwright test",
"test:e2e:headed": "playwright test --headed",
"test:e2e:ui": "playwright test --ui"
```

### 2.6 Cibles Makefile

Nouvelles cibles à ajouter dans `Makefile` :

```
test-e2e:
	docker compose -f docker-compose.dev.yml exec app yarn test:e2e

test-e2e-headed:
	yarn test:e2e:headed   # hors conteneur, navigateur visible
```

## Section 3 — Workflow CI GitHub Actions

### 3.1 Fichier `.github/workflows/ci.yml`

Structure :

```yaml
name: CI

on:
  pull_request:
    branches: [development, main]
  push:
    branches: [development, main]

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - checkout
      - setup-node 22 (with yarn cache)
      - yarn install --frozen-lockfile
      - yarn lint

  typecheck:
    runs-on: ubuntu-latest
    steps:
      - checkout
      - setup-node 22 (with yarn cache)
      - yarn install --frozen-lockfile
      - npx prisma generate
      - yarn tsc --noEmit

  unit:
    runs-on: ubuntu-latest
    services:
      mysql:
        image: mysql:8
        env:
          MYSQL_ROOT_PASSWORD: root
          MYSQL_DATABASE: badge_test
        ports: ['3306:3306']
        options: >-
          --health-cmd="mysqladmin ping -uroot -proot"
          --health-interval=5s
          --health-timeout=3s
          --health-retries=20
    env:
      DATABASE_URL: mysql://root:root@127.0.0.1:3306/badge_test
    steps:
      - checkout
      - setup-node 22 (with yarn cache)
      - yarn install --frozen-lockfile
      - npx prisma generate
      - npx prisma db push --skip-generate
      - yarn test

  e2e:
    runs-on: ubuntu-latest
    services:
      mysql: (idem job unit)
    env:
      DATABASE_URL: mysql://root:root@127.0.0.1:3306/badge_test
      NEXTAUTH_SECRET: test-secret-not-for-prod
      NEXTAUTH_URL: http://localhost:3000
      E2E_BASE_URL: http://localhost:3000
    steps:
      - checkout
      - setup-node 22 (with yarn cache)
      - yarn install --frozen-lockfile
      - npx playwright install --with-deps chromium
      - npx prisma generate
      - npx prisma db push --skip-generate
      - npx tsx prisma/seed.ts
      - yarn build
      - yarn start &
      - npx wait-on http://localhost:3000
      - yarn test:e2e
      - upload artifact playwright-report/ (on failure)
```

### 3.2 Durées cibles

| Job | Durée cible | Si dépassée |
|---|---|---|
| `lint` | < 1 min | Investiguer (rare). |
| `typecheck` | < 2 min | Cache Prisma à revoir. |
| `unit` | < 3 min | Probable régression sur le seed ou MySQL. |
| `e2e` | < 8 min | Réduire le nombre de specs E2E ou paralléliser via `--shard`. |

Si total > 12 min en moyenne sur 2 semaines, ré-architecturer (sharding, jobs séparés par feature).

### 3.3 Variables d'environnement CI

Aucun secret réel ne doit être nécessaire pour la CI :

- `DATABASE_URL` → MySQL local au runner.
- `NEXTAUTH_SECRET` → valeur publique de test, marquée comme telle.
- `NEXTAUTH_URL` → `http://localhost:3000`.
- Pas de SMTP réel : les tests qui touchent au mail mockent ou utilisent un transport fake (cohérent avec mailpit en dev).
- Pas de S3/MinIO en CI au démarrage : si tests d'upload nécessaires plus tard, ajouter un service `minio/minio` au job concerné.

### 3.4 Statut bloquant

La CI **bloque le merge** dès qu'un des 4 jobs échoue. Mais l'imposition vient de la **branch protection rule** côté GitHub, pas du repo lui-même.

## Section 4 — Branch protection (configuration GitHub manuelle)

À configurer dans `Settings → Branches → Branch protection rules` pour `development` et `main` :

| Réglage | Valeur |
|---|---|
| Require a pull request before merging | ✅ |
| Require approvals | 0 ou 1 selon préférence (solo dev = 0 OK) |
| Require status checks to pass before merging | ✅ |
| Status checks required | `lint`, `typecheck`, `unit`, `e2e` |
| Require branches to be up to date before merging | ✅ |
| Require conversation resolution before merging | ✅ |
| Do not allow bypassing the above settings | ✅ |

Cette configuration doit être documentée dans un nouveau fichier `docs/v2/ci.md` (créé dans le plan d'impl.) avec une checklist d'activation.

## Section 7 — Critères d'acceptation de l'implémentation

L'implémentation de cette spec est considérée terminée quand :

1. `cypress/` est supprimé du repo.
2. `@playwright/test` est installé et `playwright.config.ts` existe à la racine.
3. Au moins **un test E2E** existe et passe localement (`make test-e2e`) — par exemple le parcours login staff.
4. Les cibles `make test-e2e` et `make test-e2e-headed` existent dans le `Makefile`.
5. `.github/workflows/ci.yml` existe et tourne sans erreur sur une PR de test (les 4 jobs sont verts).
6. `CLAUDE.md` projet contient la nouvelle section « Politique de tests ».
7. `.claude/CLAUDE.md` contient la mention des trois couches de tests dans la section §4.
8. `docs/v2/ci.md` documente la configuration des branch protection rules et l'architecture du workflow CI.
9. `docs/v2/README.md` référence la spec v3-03 et le plan associé dans son index.

## Section 8 — Hors périmètre (YAGNI explicite)

- **Couverture chiffrée** (% de lignes) : pas pour l'instant. À reconsidérer si on observe régulièrement des PRs avec tests creux ou des trous évidents.
- **Tests de performance / load testing** : hors périmètre. À traiter dans une spec dédiée si besoin.
- **Tests de sécurité automatisés** (SAST, dependency scan) : hors périmètre. Dependabot suffit au démarrage.
- **Multi-navigateur Playwright** : chromium uniquement au démarrage. Firefox/Webkit ajoutés si bug navigateur-spécifique constaté.
- **Tests visuels (screenshots regression)** : hors périmètre. Bruyant, coûteux à maintenir, peu de valeur ajoutée à ce stade.
- **Tests mobiles** : hors périmètre tant que l'app n'a pas de version mobile dédiée.
- **CI déploiement Phase 2** : déjà traité en annexe de v3-02, pas de chevauchement.
